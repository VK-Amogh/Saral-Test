**Agent:** `explorer_m1_3` (M1 Storage & Realtime Explorer)

**Milestone:** M1 (Backend Foundation / Supabase Migration)

## 1. Executive Summary

This report establishes the authoritative specification and implementation design for **Supabase Storage** and **Supabase Realtime** within `supabase/migrations/0001_init.sql` for Saral AI.

The primary security objectives are:
1. **Private, isolated document storage:** Private bucket `documents` with path-based folder isolation (`<user_id>/<task_id>.pdf`), ensuring user A can never view user B's documents.
2. **Client mutation lockdown:** Clients possess zero write permissions (`INSERT`, `UPDATE`, `DELETE`) on storage objects. All file uploads, replacements, and deletions are strictly executed by the trusted backend / Playwright worker using the Supabase Service Role key after undergoing 5-stage document security validation.
3. **Realtime event streaming with RLS & zero PII leaks:** Tables `tasks`, `task_events`, and `messages` are published via `supabase_realtime` with `REPLICA IDENTITY FULL` to guarantee reliable state streaming to Flutter clients under strict RLS, while ensuring raw OTPs, CAPTCHA answers, and unmasked Aadhaar numbers are never present in broadcast payloads.

## 2. Storage Bucket Architecture (`documents`)

### 2.1 Bucket DDL Specification
The `documents` bucket must be created as a **private** bucket in the `storage.buckets` table:

```sql
-- Create private 'documents' bucket idempotently
insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values (
  'documents',
  'documents',
  false,
  10485760, -- 10 MB limit (exceeds max portal PDF size of ~5MB, protects against disk bloat)
  array['application/pdf']
)
on conflict (id) do update set
  public = false,
  file_size_limit = 10485760,
  allowed_mime_types = array['application/pdf'];
```

*Note on standard baseline vs defense-in-depth:*  
The baseline requirement in `SARAL_AI_IMPLEMENTATION_PLAN.md` Section 4 is:
```sql
insert into storage.buckets (id, name, public) values ('documents','documents', false)
  on conflict (id) do nothing;
```
Adding `file_size_limit = 10485760` (10 MB) and `allowed_mime_types = array['application/pdf']` adds defense-in-depth at the storage engine level. If strict adherence to the minimal schema is preferred, `insert into storage.buckets (id, name, public) values ('documents','documents', false) on conflict (id) do nothing;` is fully supported.

### 2.2 Access Semantics of Private Bucket (`public = false`)
- In Supabase Storage, setting `public = false` disables unauthenticated CDN access via `/storage/v1/object/public/documents/...`. Any request to the public URL returns `400/404` or `Unauthorized`.
- Retrieval can only occur via:
  1. Authenticated API calls `/storage/v1/object/authenticated/documents/...` where the user presents a valid Supabase JWT and satisfies the `storage.objects` RLS policy.
  2. Temporary signed URLs (`/storage/v1/object/sign/documents/...`) generated by the backend API using the `service_role` key via `create_signed_url('documents', storage_path, 60)` with a 60-second TTL.

### 2.3 Storage Path Convention
The system strictly enforces the two-level path schema:
```text
documents/<user_id>/<task_id>.pdf
```
Where:
- `bucket_id`: `'documents'`
- `name`: `'<user_id>/<task_id>.pdf'`
- `<user_id>`: UUIDv4 of the owning user (matching `auth.users(id)` and `public.profiles(id)`).
- `<task_id>`: UUIDv4 of the associated task (matching `public.tasks(id)` and `public.documents(task_id)`).
- Extension: `.pdf`

This path is mirrored in `public.documents.storage_path` as a `not null unique` column.

## 3. Storage Row Level Security (RLS) & Path Isolation

### 3.1 Policy DDL Specification
```sql
-- Ensure Row Level Security is active on storage.objects
alter table storage.objects enable row level security;

-- Client read policy with folder isolation
drop policy if exists "read own files" on storage.objects;
create policy "read own files" on storage.objects
  for select to authenticated
  using (
    bucket_id = 'documents'
    and (storage.foldername(name))[1] = auth.uid()::text
  );
```

### 3.2 Technical Analysis of Policy Mechanics

1. **Role Scope (`to authenticated`):**
   - Only requests containing a verified user JWT (the `authenticated` role) are evaluated.
   - Unauthenticated callers (`anon` role) are immediately rejected by Postgres RLS.

2. **Bucket Scope (`bucket_id = 'documents'`):**
   - The policy applies exclusively to the `documents` bucket, preventing unintended access to other storage buckets.

3. **Folder Isolation Predicate (`(storage.foldername(name))[1] = auth.uid()::text`):**
   - `storage.foldername(name)` is a Supabase PL/pgSQL function that splits `name` on the `/` delimiter and returns the directory components as a `text[]` array.
   - For `name = 'a47b1e42-7065-4f33-911e-9679f046ba2b/981fc910-c118-472e-8a03-7cb31c3bf79a.pdf'`:
     - `storage.foldername(name)` returns `ARRAY['a47b1e42-7065-4f33-911e-9679f046ba2b']`.
     - In PostgreSQL 1-indexed arrays, `[1]` extracts `'a47b1e42-7065-4f33-911e-9679f046ba2b'`.
     - `auth.uid()::text` extracts the authenticated caller's UUID from the JWT claims.
     - Access is granted if and only if the top-level directory matches the caller's UUID.

4. **Edge Cases & Path Traversal Mitigations:**
   - **Root-level file attempt (`name = 'malicious.pdf'`):**
     `storage.foldername('malicious.pdf')` returns an empty array `ARRAY[]::text[]`. In Postgres, `(ARRAY[]::text[])[1]` is `NULL`. `NULL = auth.uid()::text` evaluates to `NULL` (falsy in SQL boolean checks), so access is **denied**.
   - **Cross-user access (`name = '<user_b_id>/<task_id>.pdf'`):**
     `(storage.foldername(name))[1]` evaluates to `<user_b_id>`. `<user_b_id> = <user_a_id>` is `FALSE`, so access is **denied**.
   - **Directory traversal attempt (`name = '<user_a_id>/../<user_b_id>/<task_id>.pdf'`):**
     Supabase Storage API sanitizes and normalizes path keys before storing in `storage.objects.name`. Furthermore, `(storage.foldername(name))[1]` strictly checks the first array element, which must match `auth.uid()::text`.
   - **Deeply nested paths (`name = '<user_a_id>/subfolder/<task_id>.pdf'`):**
     The first element `[1]` remains `<user_a_id>`, though the application convention strictly produces `<user_id>/<task_id>.pdf`.

## 4. Client Mutation Lockdown & Service Role Privilege Model

### 4.1 Strict Default-Deny on INSERT, UPDATE, DELETE
In PostgreSQL RLS:
- If a table has RLS enabled and **no policy** is defined for a given operation (`INSERT`, `UPDATE`, `DELETE`) for a role, PostgreSQL enforces a **strict default-deny**.
- Therefore, by creating **only** the `for select` policy and deliberately omitting any `insert`, `update`, or `delete` policies for `authenticated` or `anon`:
  - `authenticated` clients CANNOT upload files directly via `supabase.storage.from('documents').upload(...)`.
  - `authenticated` clients CANNOT overwrite or replace files.
  - `authenticated` clients CANNOT delete files directly via storage APIs.

### 4.2 Why Direct Client Writes Must Be Forbidden
1. **PDF Authenticity & Verification Integrity:**
   - In Saral AI, downloaded government documents (e-Aadhaar) must pass the 5-point document security verifier in `backend/app/worker/verifier.py`:
     1. Valid `%PDF-` magic header bytes.
     2. File size within bounded limits (50 KB to 5 MB).
     3. Valid internal PDF cross-reference structure (via `pypdf`).
     4. Absence of malicious active content (scans for `/JavaScript`, `/JS`, `/Launch` dictionaries).
     5. Cryptographic SHA-256 integrity hash calculation.
   - If clients could upload directly, a compromised or malicious client could inject arbitrary, corrupt, or malicious payloads into the system.
2. **Auditability & Traceability:**
   - Storage uploads occur only after task state transitions from `DOWNLOADING` to `VERIFYING` and the verifier actor confirms success.
   - Direct client writes would circumvent task state machine integrity.

### 4.3 Service Role Operational Workflow
1. **Upload Workflow (Worker):**
   - The Playwright worker intercepts the portal download into a temporary isolated directory.
   - The worker executes the 5-point security verification.
   - The worker uses the Supabase Python SDK initialized with `SUPABASE_SERVICE_ROLE_KEY`:
     ```python
     # Bypasses RLS due to service_role privileges
     supabase_admin.storage.from_("documents").upload(
         path=f"{user_id}/{task_id}.pdf",
         file=verified_pdf_bytes,
         file_options={"content-type": "application/pdf", "upsert": "false"}
     )
     ```
2. **Download Workflow (Flutter App via Backend):**
   - Flutter app requests download via `GET /api/v1/tasks/{id}/download`.
   - FastAPI verifies user owns the task (`user_id == jwt.uid`).
   - FastAPI queries `public.documents` to retrieve `storage_path`.
   - FastAPI generates a signed URL with a 60-second TTL:
     ```python
     res = supabase_admin.storage.from_("documents").create_signed_url(
         path=document["storage_path"],
         expires_in=60
     )
     return {"download_url": res["signedURL"], "expires_in": 60}
     ```
   - Flutter app fetches the PDF via the temporary signed URL and saves it to the encrypted local vault.
3. **Deletion Workflow (User or Retention Sweep):**
   - When a user deletes a document via `DELETE /api/v1/documents/{id}` or the hourly retention cleanup sweep runs (`POST /internal/cleanup`):
     - FastAPI verifies ownership or cleanup secret.
     - FastAPI deletes the database row in `public.documents`.
     - FastAPI deletes the object from `documents` bucket using `supabase_admin.storage.from_("documents").remove([storage_path])`.

## 5. Realtime Publication Architecture

### 5.1 Realtime Publication DDL
The specification mandates adding `tasks`, `task_events`, and `messages` to the `supabase_realtime` publication:

```sql
-- Publication configuration
alter publication supabase_realtime add table public.tasks, public.task_events, public.messages;
```

### 5.2 Idempotency Safeguard for Migrations
In PostgreSQL, executing `ALTER PUBLICATION ... ADD TABLE` when a relation is already present raises:
`ERROR: relation "tasks" is already member of publication "supabase_realtime"`.

To guarantee that `0001_init.sql` can run cleanly in CI, local development, or repeat runs, use this idempotent block:

```sql
do $$
begin
  -- Ensure publication exists
  if not exists (select 1 from pg_publication where pubname = 'supabase_realtime') then
    create publication supabase_realtime;
  end if;

  -- Add public.tasks if not already added
  if not exists (
    select 1 from pg_publication_tables
    where pubname = 'supabase_realtime' and schemaname = 'public' and tablename = 'tasks'
  ) then
    alter publication supabase_realtime add table public.tasks;
  end if;

  -- Add public.task_events if not already added
  if not exists (
    select 1 from pg_publication_tables
    where pubname = 'supabase_realtime' and schemaname = 'public' and tablename = 'task_events'
  ) then
    alter publication supabase_realtime add table public.task_events;
  end if;

  -- Add public.messages if not already added
  if not exists (
    select 1 from pg_publication_tables
    where pubname = 'supabase_realtime' and schemaname = 'public' and tablename = 'messages'
  ) then
    alter publication supabase_realtime add table public.messages;
  end if;
end $$;
```

### 5.3 Critical Requirement: `REPLICA IDENTITY FULL`

**The Problem:**  
By default in PostgreSQL, tables use `REPLICA IDENTITY DEFAULT`. For `UPDATE` and `DELETE` events, PostgreSQL WAL only logs primary key columns for the old tuple.  
In `public.tasks`, the primary key is `id`, but RLS and Flutter Realtime subscriptions filter on `user_id`.  
When a task transitions states (e.g., from `RUNNING` to `WAITING_FOR_USER` or `COMPLETED`), an `UPDATE` occurs. If `REPLICA IDENTITY` is `DEFAULT`:
1. Supabase Realtime cannot verify non-primary-key RLS predicates for old rows.
2. CDC streams cannot evaluate column filters (such as `filter: user_id=eq.<uid>`).

**The Solution:**  
The migration MUST set `REPLICA IDENTITY FULL` on all published tables that undergo updates or require filtered subscriptions:

```sql
alter table public.tasks replica identity full;
alter table public.task_events replica identity full;
alter table public.messages replica identity full;
```

With `REPLICA IDENTITY FULL`, the entire previous row image is written to the WAL, allowing Supabase Realtime to correctly evaluate RLS and column filters on every state update.

## 6. Realtime Security & Zero-Leak Payload Invariants

### 6.1 RLS Enforcement on Realtime Broadcasts
Supabase Realtime respects PostgreSQL Row Level Security:
- When a client subscribes to a channel with a user JWT, Supabase Realtime checks the table's `SELECT` RLS policy against the user's `auth.uid()`.
- Because `tasks`, `task_events`, and `messages` have `for select using (user_id = auth.uid())`:
  - User A is mathematically prevented from receiving change events for User B's tasks, events, or messages.
  - Even if User A connects a malicious WebSocket without a `user_id` filter, Supabase Realtime filters the outgoing events against User A's JWT.

### 6.2 Zero-Leak Verification on Column Payloads
The Acceptance Criteria in `ORIGINAL_REQUEST.md` (lines 69–70) mandate:
> "OTP and CAPTCHA values are never persisted to Postgres, logged to console, sent to Supabase Realtime, or passed into any LLM prompt."
> "Automated audit scan across backend logs, database rows, and Realtime messages confirms 0 occurrences of unmasked Aadhaar numbers, OTPs, or sensitive tokens."

Here is how each table published to Realtime satisfies this invariant:

| Published Table | Monitored Columns | Content Guarantee | Leak Prevention Mechanism |
|---|---|---|---|
| `public.tasks` | `pending_input` | Challenge metadata only: `{"kind": "OTP", "prompt": "Enter 6-digit OTP", "expires_in": 180, "attempts_left": 3}` | Raw OTP codes and CAPTCHA text are NEVER stored. OTP input is handled in-memory via `SecretStr` in Challenge Broker. |
| `public.tasks` | `request_text` | Scrubbed prompt | Masked by `pii_scrubber.py` before task creation. |
| `public.task_events` | `message` | Operational progress strings (e.g. "Solving portal challenge...", "Identity verified") | No credentials or PII ever inserted into events. |
| `public.messages` | `content` | Chat message text | PII scrubber masks Aadhaar to `XXXX-XXXX-1234`, phone to `[REDACTED_PHONE]`, email to `[REDACTED_EMAIL]`, OTP mentions to `[REDACTED_OTP]` BEFORE insertion. |

*Note on CAPTCHA images:*  
CAPTCHA challenge images are served exclusively in-memory via `GET /api/v1/tasks/{id}/challenge` with `Cache-Control: no-store`. They are NEVER inserted into PostgreSQL and NEVER transmitted over Realtime.

### 7.1 Storage RLS & Path Isolation Verification Script (SQL)
Run this SQL script against the database to test positive and negative access permissions:

```sql
-- ============================================================================
-- VERIFICATION TEST SUITE: STORAGE RLS & PATH ISOLATION
-- ============================================================================

do $$
declare
  user_a uuid := gen_random_uuid();
  user_b uuid := gen_random_uuid();
  test_task_a uuid := gen_random_uuid();
  test_task_b uuid := gen_random_uuid();
  path_a text;
  path_b text;
  can_read boolean;
begin
  path_a := user_a::text || '/' || test_task_a::text || '.pdf';
  path_b := user_b::text || '/' || test_task_b::text || '.pdf';

  -- 1. Verify bucket exists and is private
  assert exists (
    select 1 from storage.buckets where id = 'documents' and public = false
  ), 'Assertion Failed: documents bucket must exist and public = false';

  -- 2. Verify RLS is enabled on storage.objects
  assert exists (
    select 1 from pg_tables
    where schemaname = 'storage' and tablename = 'objects' and rowsecurity = true
  ), 'Assertion Failed: storage.objects must have RLS enabled';

  -- 3. Verify 'read own files' policy exists for SELECT
  assert exists (
    select 1 from pg_policies
    where schemaname = 'storage' and tablename = 'objects'
      and policyname = 'read own files' and cmd = 'SELECT'
  ), 'Assertion Failed: read own files policy must exist for SELECT';

  -- 4. Verify NO INSERT, UPDATE, or DELETE policies exist for authenticated/anon
  assert not exists (
    select 1 from pg_policies
    where schemaname = 'storage' and tablename = 'objects'
      and cmd in ('INSERT', 'UPDATE', 'DELETE')
      and ('authenticated' = any(roles) or 'anon' = any(roles) or 'public' = any(roles))
  ), 'Assertion Failed: No INSERT/UPDATE/DELETE policies should exist for users on storage.objects';

  -- 5. Test path parsing logic in SQL
  assert (storage.foldername(path_a))[1] = user_a::text,
    'Assertion Failed: foldername must match user_a';
  assert (storage.foldername(path_b))[1] = user_b::text,
    'Assertion Failed: foldername must match user_b';
  assert (storage.foldername(path_b))[1] <> user_a::text,
    'Assertion Failed: cross-user foldername must not match';
  assert (storage.foldername('flat_file.pdf'))[1] is null,
    'Assertion Failed: root level file must yield null folder';

  raise notice 'All Storage RLS assertions passed successfully.';
end $$;
```

### 7.4 Realtime Payload Zero-Leak Verification (Python / `pytest`)

```python
import pytest
import re

AADHAAR_REGEX = re.compile(r"\b\d{4}\s?\d{4}\s?\d{4}\b")
OTP_REGEX = re.compile(r"\b\d{6}\b")

def test_realtime_payload_zero_leak(realtime_events_captured):
    """
    Scans captured Realtime payloads for tasks, task_events, and messages
    to verify zero leak of unmasked Aadhaar, OTPs, or CAPTCHA answers.
    """
    for event in realtime_events_captured:
        payload = event.get("new", {})
        table = event.get("table")

        if table == "tasks":
            pending = payload.get("pending_input")
            if pending:
                # Must never contain "value" or raw code
                assert "value" not in pending
                assert "otp" not in pending
                assert "captcha_answer" not in pending

        if table == "task_events":
            msg = payload.get("message", "")
            # Ensure no 6-digit raw OTP in progress message
            assert not OTP_REGEX.search(msg)

        if table == "messages":
            content = payload.get("content", "")
            # Ensure no unmasked 12-digit Aadhaar number
            unmasked = [m for m in AADHAAR_REGEX.findall(content) if not m.startswith("XXXX")]
            assert len(unmasked) == 0, f"Unmasked Aadhaar leaked in message: {content}"
```
